Why we set this up

Claude does not know our standards - until the repo teaches them

  • Every new session starts blank. Without setup files, you re-explain your standards every time - and you forget things.
  • Unguided Claude writes generic Salesforce code. SOQL inside loops, no CRUD/FLS checks, tests without real assertions.
  • Review becomes the bottleneck. Writing is the fast part; fixing what review catches is the slow part.
  • The fix: write the standards down once, in the repo. Claude reads them every session, and the pipeline proves them on every pull request.
The one rule underneath everything

AI-written code meets exactly the same standard as human-written code. The setup exists to make that cheap, not to lower the bar.

Build it in this order

2
Setup - step 2 of 5: CLAUDE.md

CLAUDE.md - the file Claude reads at the start of every session

If you do only one thing

Write a good CLAUDE.md - the highest-leverage file in this setup.

  • What goes in: the project overview in 3-5 lines, the exact sf commands, our Apex/LWC standards, the definition of done.
  • Naming conventions belong here too - the short list itself, or a pointer to docs/naming-conventions.md once it grows. Claude reads it every session, so AI-written code follows our names and review stops being about names.
  • Keep it short. Every line loads into every session, so every line costs tokens forever. The test: would removing it cause mistakes? If not, cut it.
  • Start with /init - Claude analyzes the repo and drafts the file. Run /context to see what loaded.
  • Shared vs personal: ./CLAUDE.md in git is shared; ~/.claude/CLAUDE.md is yours; split a growing file with @imports.

Why this works: concise always-on instructions are followed; bloated files get ignored.

3
Setup - step 3 of 5: rules

Rules load only for the files being edited - that is the point

# .claude/rules/apex.md
---
paths: ["**/*.cls", "**/*.trigger"]
---
# Loaded only while Claude edits Apex. Costs zero tokens
# when the work is a Flow or a YAML file.
  • One file per topic: apex.md, lwc.md, flows.md, omnistudio.md, testing.md, git.md.
  • This is where the depth lives: bulkification, sharing and CRUD/FLS, trigger discipline, async choice, test standards - the details that used to be tribal knowledge.
  • Less irrelevant context means better answers and fewer tokens spent.

Why this works: conditional loading keeps the context window for the task at hand. CLAUDE.md holds what is always true; rules hold what is true for this file type.

4
Setup - step 4 of 5: skills

Skills: our procedures, written down once

/apex-review

Reviews edited Apex against our rules: bulkification, CRUD/FLS, sharing, ApexDoc.

/deploy-validate

Deploy + test + scan a scratch org, in the right order, with proof at each step.

/scratch-org-setup

Creates and seeds a scratch org the same way, every time.

  • A skill is a SKILL.md in .claude/skills/ - a written procedure Claude runs when the task matches. No more re-explaining your deploy ritual.
  • Skill vs CLAUDE.md: universal standards go in CLAUDE.md (always on); task procedures go in skills (loaded when needed).
  • Frontmatter controls blast radius: context: fork runs it isolated; allowed-tools restricts what it may call; disable-model-invocation keeps side-effect workflows manual.

Why this works: reusable workflows are encoded once and invoked on demand. Write your first skill for whatever the team re-explains most often.

5
Setup - step 5 of 5: hooks (optional)

Hooks: add them when advice must become enforcement

The design rule

CLAUDE.md advises. Hooks enforce. Start without them; add one the first time a standard gets ignored.

  • Deny list in settings.json - Claude cannot run sf org delete or deploy to production aliases.
  • PostToolUse hook - scans every Apex file Claude edits for SOQL/DML in loops, hardcoded IDs, SeeAllData, empty catches.
  • Stop hook - Claude cannot end the session until tests pass and the scanner is clean.
  • Prompt instructions fail some percent of the time. For a non-negotiable, that failure rate is the argument for a hook.

Why this works: deterministic steps get programmatic enforcement; judgment calls stay as prompt guidance. Template in .claude/settings.json - delete it if you do not want hooks yet.

The pipeline (1 of 2)

Component unit tests on every PR.

JOB 2
Apex tests

Scratch org created in CI, tests run with coverage.

GATE
85% coverage

Below the gate, the PR cannot merge.

ALWAYS

An independent Claude instance reviews the diff and comments.

Workflow files: ci-templates/ in the starter repo - one README command copies them into .github/workflows/.

The pipeline (2 of 2)

A fresh Claude reviews every PR - on purpose

  • Self-review is weak review. The session that wrote the code keeps its reasoning and defends its choices. An independent instance catches what the author misses.
  • Headless in pipelines: claude -p "..." --output-format json - machine-parseable findings posted as PR comments.
  • The review prompt carries explicit criteria from our rules, not "be conservative" - vague instructions raise false positives and erode trust.
  • Findings must cite evidence - the file, the line, the rule violated. A comment without a pointer is opinion; with one, it is actionable.
  • @claude in any PR comment summons help with full repo context (Claude Code Action, installed once).

Why this works: an independent review instance with explicit criteria outperforms author self-review. Source: github.com/anthropics/claude-code-action.

Using it well (1 of 6)

Plan first, then execute

PLAN MODE

Anything architectural: multi-file changes, data migrations, several valid approaches, touching a trigger framework. Explore and design first, implement after.

DIRECT EXECUTION

Well-scoped changes: a single-file bug fix with a clear stack trace, one validation check, a rename.

Rule of thumb

If the wrong approach would cost more than the planning would, plan first. Start the plan from the outcome - what should be true when this is done? A testable success criterion ("the trigger handles 200 records and the test proves it") is how Claude knows it is finished. The daily rhythm: explore, plan, implement, commit - four separate steps, not one prompt.

Why this works (the official best-practices guide): separating research and planning from implementation avoids solving the wrong problem.

Using it well (2 of 6)

Prompts that get it right the first time

  • Show, don't describe. We pasted one short ApexDoc example into CLAUDE.md - Claude rewrote a poorly documented class in exactly our style. Two or three concrete examples outperform any paragraph of rules.
  • Test-driven loop: write the tests first, then iterate by sharing failures. Each failure message is a precise instruction.
  • The interview pattern: on unfamiliar work, tell Claude to ask you questions before implementing - then start a fresh session to execute the spec it writes.
  • Correct early. Stop Claude the moment it drifts (Esc), rewind when an approach fails (Esc Esc). Two failed corrections in one session: /clear and restart with a sharper prompt.

Why this works: few-shot examples and precise context beat adjectives. The ApexDoc example ships in the starter repo's CLAUDE.md.

Using it well (3 of 6)

Split big work across a coordinator and sub-agents

  • Hub and spoke: one coordinator decomposes the task, spawns sub-agents, aggregates results. Sub-agents never talk to each other directly.
  • Sub-agent context is isolated. They inherit nothing automatically - the coordinator passes complete, structured findings in the prompt.
  • Decompose by question, not by file: each sub-agent gets one question it can answer alone - a goal and the evidence it needs, not a rigid script.
  • Spawn in parallel: independent investigations go out as multiple Task calls in one turn.
  • Scope the tools: 4-5 relevant tools per agent beats 18 - tool overload degrades selection reliability. Same for MCP: connect only the servers the task actually needs.
  • Custom sub-agents live in .claude/agents/ - our example: a security reviewer that checks CRUD/FLS, sharing, and injection on demand.

Why this works: orchestration with isolated contexts is the core agentic architecture pattern.

Using it well (4 of 6)

Keep the context window clean

  • The symptom of decay: Claude starts citing "typical patterns" instead of the classes it read an hour ago. Performance degrades as the window fills.
  • Keep exploration out of the main context: an Explore subagent reads widely and returns a summary; context: fork skills do the same.
  • Persist findings to scratchpad files in the repo; they survive compaction and crashes.
  • Handoffs stand alone: write the summary so a fresh session picks up the work without the old one - then start fresh instead of resuming a decayed session.
  • /clear between unrelated tasks. /compact early, with instructions in CLAUDE.md about what must survive. A fresh session with a written summary beats resuming a rotten one.

Why this works: the context window is the most important resource to manage - treat it as a budget, not a bottomless pit.

Using it well (5 of 6)

Match the model to the task - cost follows

ModelUse for
HaikuFast, cheap, simple: file scans, formatting, classification, boilerplate.

The default

Sonnet for the day job. Drop to Haiku for grunt work, escalate to Opus when the task earns it.

Why this works: model selection is a quality-speed-cost trade-off you make per task, not a default you set once.

Using it well (6 of 6)

Fewer wasted tokens is a setup property, not willpower

  • Path-scoped rules load only for matching files - you stop paying for Apex rules while editing YAML.
  • Lean CLAUDE.md. It is prepended to every session; every line is a recurring cost.
  • Prompt caching for repeated large contexts; Message Batches API for overnight work - 50% cheaper, never for anything blocking a merge.
  • Right-size the model - the biggest single lever.

Why this works: token efficiency comes from configuration - rules, file size, caching - not from asking developers to type less.

Responsible use

The rules we all follow when Claude writes our code

  • You review everything you merge. AI-written code you have not read is still your code and your name on the commit.
  • Same bar as human code. Scanner clean, tests real, security checks present.
  • No secrets, ever. No credentials, session IDs, or customer data in prompts, CLAUDE.md, rules, or skills. MCP server tokens live in your secret store, never in the repo.
  • Production is human-run. Deploys to prod are run by a person, not by Claude.
  • Escalate doubt. If Claude's approach looks wrong, challenge it or ask a human.

The principle underneath: guardrails on anything irreversible, and a human accountable for every merge.

Get started

Set it up on your repo in about fifteen minutes

  • 1. Read the starter repo: github.com/krika2810/claude-code-sf-starter - every file commented.
  • 2. Copy it into your repo (one README command), then run /init in Claude Code and merge its draft with our CLAUDE.md.
  • 3. Add the CI templates, install the Claude Code GitHub Action, add ANTHROPIC_API_KEY to repo secrets.
  • 4. Open a PR and watch the gate run.
  • 5. Keep a few repeatable Salesforce tasks and re-run them after every setup change - that is how you know a "better" CLAUDE.md actually got better.
