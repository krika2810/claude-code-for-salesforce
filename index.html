CLAUDE CODE / SALESFORCE WORKSHOP
01
Developer workshop

Use Claude Code as an engineering system, not a code generator

A live workshop on the practices that make Claude Code reliable on real Salesforce work. Every practice ends with something the room can inspect live.

Practice 01

Start with the business outcome, not the prompt

WHYThe principle

A good Claude Code task begins with the result, constraints, and proof of success. The prompt is an implementation detail, not the design.

HOWWhat developers do

Define: user outcome, affected Salesforce surface, non-negotiable constraints, and acceptance evidence. Keep architecture proportional to the job.

Live workshop cue
Show it in Claude Code

Ask Claude to turn “improve account creation” into a one-page brief: users, flow, constraints, acceptance tests, and open questions.

Practice 02

Choose the lightest pattern that can do the job

WHYThe principle

Use a direct answer for a small change, a fixed workflow for known steps, and an agentic workflow only when the next step depends on what Claude discovers.

HOWWhat developers do

Decision rule: direct edit for clear scope; plan and chain for predictable stages; agentic loop for open-ended investigation. Complexity must earn its cost.

Live workshop cue
Show it in Claude Code

Run the same Apex bug three ways. Show why a one-file null check needs direct execution while an unknown governor-limit failure needs investigation.

Practice 03

Make success testable before Claude writes code

WHYThe principle

Turn “good”, “secure”, and “fast” into observable criteria. Claude performs better when it can check its own work against evidence.

HOWWhat developers do

State exact behavior, edge cases, limits, files allowed to change, and the command or test that proves completion. Avoid vague confidence language.

Live workshop cue
Show it in Claude Code

Give Claude a failing Apex test for bulk Account creation and ask it to make the test pass without changing the test or public contract.

Practice 04

Put stable team knowledge in the repository

WHYThe principle

CLAUDE.md should hold facts that apply to most tasks: architecture, commands, repo map, hard constraints, and what “done” means.

HOWWhat developers do

Keep shared knowledge at project level. Split detailed standards into focused files and import them. Personal preferences stay user-level.

Live workshop cue
Show it in Claude Code

Open a blank session, ask where Account creation starts, then add a short repo map to CLAUDE.md and repeat. Compare search time and answer quality.

Practice 05

Load rules only when the file needs them

WHYThe principle

Conditional rules keep instructions relevant. They reduce context noise and prevent LWC rules from competing with Apex rules.

HOWWhat developers do

Use path-scoped rules for conventions spread across directories. Put only universal guidance in CLAUDE.md. Treat context as a budget.

Live workshop cue
Show it in Claude Code

Create apex.md for **/*.cls and lwc.md for **/lwc/**. Edit one file of each type and use /context to show what loaded.

Practice 06

Teach judgment with examples, not more prose

WHYThe principle

When a requirement is interpreted inconsistently, two or three examples usually beat another page of instructions. Include close calls and non-examples.

HOWWhat developers do

Show acceptable and unacceptable patterns, the reason, and expected output shape. Examples teach boundaries, not just formatting.

Live workshop cue
Show it in Claude Code

Give Claude one bulk-safe trigger example, one query-in-loop anti-example, and one ambiguous helper. Ask it to classify a new class and explain the boundary.

Practice 07

Plan when the cost of being wrong is high

WHYThe principle

Plan mode is for architecture, many files, unknown dependencies, or several valid approaches. Direct execution is for a small, understood change.

HOWWhat developers do

During planning, ask for code paths, risks, alternatives, test impact, and an explicit file-change map. Approve the plan before edits.

Live workshop cue
Show it in Claude Code

Use plan mode to move Person Account creation from Flow logic into an invocable Apex service. Ask for two designs and trade-offs, then choose one.

Practice 08

Explore large codebases in narrow passes

WHYThe principle

Reading everything floods context. Find entry points first, follow references, record facts, and delegate noisy searches away from the main thread.

HOWWhat developers do

Use Glob for names, Grep for symbols and messages, then Read only the files on the path. Persist a compact map in a scratchpad.

Live workshop cue
Show it in Claude Code

Ask an Explore subagent to trace Account creation from LWC to Apex to Flow and return only files, entry points, and unresolved branches.

Practice 09

Turn repeatable work into a skill

WHYThe principle

A skill packages a procedure, quality bar, and allowed tools. It should activate for a recognizable job, not become a second CLAUDE.md.

HOWWhat developers do

Use project skills for team workflows. Fork verbose analysis and restrict allowed tools. Require arguments when missing parameters would cause guessing.

Live workshop cue
Show it in Claude Code

Build /apex-review with context: fork and read-only tools. Run it on one class and inspect the compact report returned to the main session.

Practice 10

Give every tool one clear job

WHYThe principle

Claude selects tools from their names and descriptions. Overlap creates random routing; vague descriptions create wrong calls.

HOWWhat developers do

Describe when to use the tool, inputs, outputs, edge cases, and how it differs from similar tools. Split broad tools by intent.

Live workshop cue
Show it in Claude Code

Compare “query_salesforce” with separate “find_accounts_by_email” and “load_account_by_id”. Ask Claude which tool fits three requests.

Practice 11

Give each agent only the tools its role needs

WHYThe principle

More tools do not mean more capability. They increase selection errors and widen the damage a mistaken agent can cause.

HOWWhat developers do

A researcher reads; an implementer edits; a reviewer stays read-only. Remove unused tools instead of relying on reminders not to use them.

Live workshop cue
Show it in Claude Code

Create a read-only Apex reviewer subagent. Show that it cannot edit or deploy even if the prompt asks it to “fix everything”.

Practice 12

Scope MCP connections and secrets correctly

WHYThe principle

Share stable team integrations at project scope, keep experiments at user scope, and inject credentials through environment variables. Never commit tokens.

HOWWhat developers do

Prefer a maintained MCP server for standard systems. Build custom MCP only for a team-specific workflow. Expose catalogs as resources when discovery matters.

Live workshop cue
Show it in Claude Code

Add a read-only Salesforce metadata MCP to .mcp.json with ${SF_ACCESS_TOKEN}; show project discovery without exposing the secret.

Practice 13

Return errors Claude can act on

WHYThe principle

“Operation failed” removes the information needed for recovery. Errors should say what failed, whether retry helps, and what partial work survived.

HOWWhat developers do

Separate transient, validation, permission, and business errors. A valid empty result is not an access failure. Recover locally when safe.

Live workshop cue
Show it in Claude Code

Mock an MCP account lookup returning timeout, no match, and permission denied. Watch Claude retry only the transient case and clarify the no-match case.

Practice 14

Give Claude a goal and evidence, not a rigid script

WHYThe principle

Agentic work is useful when the next step depends on what Claude discovers. A fixed script is better when every step is already known.

HOWWhat developers do

State the outcome, allowed actions, stopping condition, and proof required. Let Claude adapt the investigation while deterministic controls protect hard boundaries.

Live workshop cue
Show it in Claude Code

Trace an unknown Account-save error: Claude searches logs, opens the named class, runs a focused test, and stops only when it can show the root cause and evidence.

Practice 15

Split work by independent questions

WHYThe principle

Good decomposition reduces overlap and lets work run in parallel. Bad decomposition creates agents that repeat the same search or cannot combine results.

HOWWhat developers do

Partition by file set, concern, or source type. Use a fixed chain for known stages and dynamic subtasks when findings change the plan.

Live workshop cue
Show it in Claude Code

Send three subagents in parallel: Apex path, Flow path, and LWC path. Then ask the coordinator for one cross-layer transaction map.

Practice 16

Use one coordinator as the control point

WHYThe principle

In a multi-agent system, the coordinator owns decomposition, context routing, retries, coverage, and final synthesis. Subagents should not form an invisible side network.

HOWWhat developers do

Give each subagent a complete task packet and quality bar. Return structured results to the coordinator, including gaps and errors.

Live workshop cue
Show it in Claude Code

Run a coordinator that decides whether an Apex-only question needs one specialist or a cross-layer issue needs Apex, Flow, and LWC specialists.

Practice 17

Pass context explicitly between agents

WHYThe principle

Subagents do not inherit the parent conversation. Missing constraints produce locally correct work that fails the real task.

HOWWhat developers do

Pass goal, relevant files, known facts, constraints, expected output, and source metadata. Use structured handoffs rather than “continue the work”.

Live workshop cue
Show it in Claude Code

First omit the bulk limit and watch a subagent design for one record. Then pass a task packet requiring 200 records and compare the implementation.

Practice 18

Use hooks only for rules that must never be optional

WHYThe principle

Prompts guide behavior; hooks enforce invariants. If one missed instruction can expose data or mutate the wrong org, use a deterministic control.

HOWWhat developers do

Intercept dangerous calls before execution. Normalize inconsistent tool output after execution. Keep judgment in prompts and guarantees in code.

Live workshop cue
Show it in Claude Code

Add a PreToolUse hook that blocks sf deploy to a production alias but allows scratch-org validation. Trigger both commands live.

Practice 19

Design handoffs for someone without the transcript

WHYThe principle

A handoff must stand alone. Include the objective, confirmed facts, files touched, evidence, unresolved risks, and the next decision.

HOWWhat developers do

Separate facts from assumptions. Keep identifiers and exact values. Never force the next agent or human to reconstruct context.

Live workshop cue
Show it in Claude Code

Pause a refactor halfway. Ask Claude for a structured handoff, start a fresh session, paste only that handoff, and continue safely.

Practice 20

Preserve critical facts outside the chat history

WHYThe principle

Long sessions compress details and lose middle content. Keep exact requirements, identifiers, and decisions in a durable working file.

HOWWhat developers do

Trim verbose tool output, put key facts first, use clear sections, and maintain a case-facts or scratchpad block that survives compaction.

Live workshop cue
Show it in Claude Code

During a long Account feature task, write task-state.md with decisions, file map, test status, and open risks. Compact, then ask Claude to resume from it.

Practice 21

Resume only when the old context is still trustworthy

WHYThe principle

A resumed session is useful when the code and assumptions remain valid. If files changed, provide a delta or start fresh with a verified summary.

HOWWhat developers do

Name important sessions. Fork to compare approaches from one baseline. Do not carry stale tool results into a changed repository.

Live workshop cue
Show it in Claude Code

Resume yesterday’s session after changing one Apex class. First show the stale answer; then inject the git diff and request targeted re-analysis.

Practice 22

Ask when ambiguity changes the outcome

WHYThe principle

Agents should not guess among multiple customers, environments, or architectural meanings. Clarify when the missing fact is load-bearing.

HOWWhat developers do

Escalate explicit human requests, policy gaps, and stalled work. Do not use sentiment or a self-reported confidence number as the trigger.

Live workshop cue
Show it in Claude Code

Ask Claude to “update the Account flow” when two active flows match. A good system returns the two API names and asks which one.

Practice 23

Force structure when another system must consume the answer

WHYThe principle

Text that looks like JSON is not a contract. Use tool schemas or forced tool choice when downstream code requires exact fields.

HOWWhat developers do

Make absent fields nullable. Validate semantics after schema validation; valid JSON can still contain the wrong totals or file names.

Live workshop cue
Show it in Claude Code

Define a finding schema: file, line, severity, evidence, fix, nullable uncertainty. Run an Apex review and inspect the tool_use payload.

Practice 24

Retry with the exact failure, not the same prompt

WHYThe principle

A retry helps when format or reasoning can be corrected. It cannot recover information that was never available.

HOWWhat developers do

Return the failed output plus specific validation errors. Stop or escalate when the source lacks the required fact. Track repeated failure patterns.

Live workshop cue
Show it in Claude Code

Reject a generated test because no assertion covers the bulk case. Feed that exact validation failure back and compare the corrected test.

Practice 25

Review with fresh context and more than one pass

WHYThe principle

The session that wrote the code is biased toward its own reasoning. An independent reviewer sees different failures. Large changes need local and cross-file passes.

HOWWhat developers do

First review each file for local defects. Then review integration, data flow, and transaction behavior across files. Preserve findings between passes.

Live workshop cue
Show it in Claude Code

Generate an Apex service in one session. Open a fresh read-only reviewer to inspect bulk behavior, then run a second pass across caller and tests.

Practice 26

Keep every claim attached to its evidence

WHYThe principle

Synthesis often drops source attribution. Require claim-source mappings and carry them through every agent and summary.

HOWWhat developers do

Record file, line, command output, URL, and date where relevant. If credible sources conflict, show the conflict instead of choosing silently.

Live workshop cue
Show it in Claude Code

Ask three subagents for findings as {claim, file, lines, evidence}. Make the coordinator reject any final finding without evidence.

Practice 27

Evaluate the system, not one impressive demo

WHYThe principle

A workshop success is repeatable performance across realistic tasks. Measure quality, latency, cost, safety, and failure recovery.

HOWWhat developers do

Build a small fixed task set, capture baselines, change one thing at a time, and inspect failures by category. Monitor drift after model or repo changes.

Live workshop cue
Show it in Claude Code

Run five saved Salesforce tasks before and after adding examples to a rule. Compare pass rate, unnecessary edits, turns, and tokens.

Practice 28

Close the loop with a reusable team playbook

WHYThe principle

A Claude Code practice becomes valuable when developers can repeat it, see why it works, and improve it from evidence.

HOWWhat developers do

For each workflow, keep the intent, inputs, allowed capabilities, acceptance test, human gate, and failure path in version control.

Live workshop cue
Show it in Claude Code

Final lab: developers choose a real Salesforce change and build the prompt, context, specialist roles, evidence gate, and handoff together.
