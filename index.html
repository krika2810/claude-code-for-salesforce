The goal

Claude writes code that passes review the first time

  • The repo teaches Claude our standards. CLAUDE.md, rules, and skills carry them; Claude reads them every session.
  • The pipeline proves them. Scanners, tests, and an independent Claude review run on every PR.
  • Hooks add hard enforcement - optional. Add them when advice alone is not enough. More on that later.
  • The bar does not change. AI-written code meets exactly the same standard as human-written code.

Core, 1 of 2: CLAUDE.md

CLAUDE.md - the file Claude reads every session

If you do only one thing

Write a good CLAUDE.md. It is the single highest-leverage file in this setup.

  • What goes in: 3-5 lines of project overview, the exact sf commands to use, our Apex/LWC standards, the definition of done, a pointer to the naming doc.
  • Keep it under ~200 lines. Long instruction files get followed less reliably. Detail moves to rules and skills.
  • Project vs personal: ./CLAUDE.md in git is the team's shared brain; ~/.claude/CLAUDE.md is personal and never shared.
  • Split with @import when it grows. Debug odd behavior with /memory - it shows exactly which files loaded.

Starter file: CLAUDE.md in the template repo, every section commented. Source: Claude Code docs + CCAR-F exam guide, Domain 3.1.

Core, 2 of 2: skills

Skills: teach Claude your procedures once

/apex-review

Reviews edited Apex against our rules: bulkification, CRUD/FLS, sharing, ApexDoc.

/deploy-validate

Deploy + test + scan a scratch org, in the right order, with proof at each step.

/scratch-org-setup

Creates and seeds a scratch org the same way, every time.

  • A skill is a SKILL.md in .claude/skills/ - a written procedure Claude runs when the task matches. No more re-explaining your deploy ritual.
  • Skill vs CLAUDE.md: universal standards go in CLAUDE.md (always on); task procedures go in skills (loaded when needed).
  • Frontmatter controls blast radius: context: fork runs it isolated; allowed-tools restricts what it may call.

Source: CCAR-F exam guide, Domain 3.2. Write your first skill for whatever the team explains most often.

Next layer: path-scoped rules

Rules load only when relevant - that is the point

# .claude/rules/apex.md
---
paths: ["**/*.cls", "**/*.trigger"]
---
# Loaded only while Claude edits Apex. Costs zero tokens
# when the work is a Flow or a YAML file.
  • One file per topic: apex.md, lwc.md, flows.md, omnistudio.md, testing.md, git.md.
  • Where the depth lives: bulkification, sharing and CRUD/FLS, trigger discipline, async choice, test standards - the details that used to be tribal knowledge.
  • Less irrelevant context = better answers and fewer tokens.

Source: CCAR-F exam guide, Domain 3.3 (conditional convention loading).

Optional layer: hooks

Hooks: not mandatory - add them when advice is not enough

The design rule

CLAUDE.md advises. Hooks enforce. Start without them; add one the first time a standard gets ignored.

  • Deny list in settings.json - Claude cannot run sf org delete or deploy to production aliases.
  • PostToolUse hook - scans every Apex file Claude edits for SOQL/DML in loops, hardcoded IDs, SeeAllData, empty catches.
  • Stop hook - Claude cannot end the session until tests pass and the scanner is clean.
  • Prompt instructions fail some percent of the time. For a non-negotiable, that failure rate is the argument for a hook.

Source: CCAR-F exam guide, Task Statements 1.4-1.5 (programmatic enforcement vs prompt guidance). Template in .claude/settings.json - delete it if you do not want hooks yet.

Claude Code inside the pipeline

A fresh Claude reviews every PR - on purpose

  • Self-review is weak review. The session that wrote the code keeps its reasoning and defends its choices. An independent instance catches what the author misses.
  • Headless in pipelines: claude -p "..." --output-format json - machine-parseable findings posted as PR comments.
  • The review prompt carries explicit criteria from our rules, not "be conservative" - vague instructions raise false positives and erode trust.
  • @claude in any PR comment summons help with full repo context (Claude Code Action, installed once).

Sources: CCAR-F exam guide Domains 3.6 + 4.6, github.com/anthropics/claude-code-action.

Using it well: orchestration

Big work gets a coordinator and sub-agents

  • Hub and spoke: one coordinator decomposes the task, spawns sub-agents, aggregates results. Sub-agents never talk to each other directly.
  • Sub-agent context is isolated. They inherit nothing automatically - the coordinator passes complete, structured findings in the prompt.
  • Spawn in parallel: independent investigations go out as multiple Task calls in one turn.
  • Scope the tools: 4-5 relevant tools per agent beats 18. Tool overload degrades selection reliability.

Source: CCAR-F exam guide, Domain 1 (27% of the exam).

Using it well: context rot

Long sessions decay. Manage context deliberately.

  • The symptom: Claude starts citing "typical patterns" instead of the classes it read an hour ago.
  • Keep exploration out of the main context: the Explore sub-agent reads widely and returns a summary; context: fork skills do the same.
  • Persist findings to scratchpad files in the repo; they survive compaction and crashes.
  • /compact early; when prior results are stale, start fresh with a written summary - it beats resuming a rotten session.

Source: CCAR-F exam guide, Domain 5 + Domain 3.4.

Using it well: token efficiency

Fewer wasted tokens is a setup property, not willpower

  • Path-scoped rules load only for matching files - you stop paying for Apex rules while editing YAML.
  • Lean CLAUDE.md (~200 lines). It is prepended to every session; every line is a recurring cost.
  • Prompt caching for repeated large contexts; Message Batches API for overnight work - 50% cheaper, never for anything blocking a merge.
  • Right-size the model - the biggest single lever.

Sources: CCAR-F exam guide Domains 4.5 + 5.1, CCAR-P Domain 2.

Using it well: plan mode

Plan mode for thinking. Direct execution for typing.

PLAN MODE

Anything architectural: multi-file changes, migrations, several valid approaches, touching a trigger framework. Explore and design first, implement after.

DIRECT EXECUTION

Well-scoped changes: a single-file bug fix with a clear stack trace, one validation check, a rename.

Rule of thumb

If the wrong approach would cost more than the planning would, plan first. Combine both: plan the migration, then execute the plan directly.

Source: CCAR-F exam guide, Domain 3.4.

Using it well: prompting

Examples beat adjectives. Tests beat descriptions.

  • Show, don't describe. We pasted one short ApexDoc example into CLAUDE.md - Claude rewrote a poorly documented class in exactly our style. Two or three concrete examples outperform any paragraph of rules.
  • Test-driven loop: write the tests first, then iterate by sharing failures. Each failure message is a precise instruction.
  • The interview pattern: on unfamiliar work, tell Claude to ask you questions before implementing.

Sources: CCAR-F exam guide Domains 3.5 + 4.2. The ApexDoc example ships in the starter repo's CLAUDE.md.

Responsible use

Rules for using Claude Code on this team

  • You review everything you merge. AI-written code you have not read is still your code and your name on the commit.
  • Same bar as human code. Scanner clean, tests real, security checks present.
  • No secrets, ever. No credentials, session IDs, or customer data in prompts, CLAUDE.md, rules, or skills.
  • Production is human-run. Deploys to prod are run by a person, not by Claude.
  • Escalate doubt. If Claude's approach looks wrong, challenge it or ask a human.

Aligned with CCAR-P exam guide, Domain 5 (governance, safety, human-in-the-loop).

Get started

Fifteen minutes to the same setup

  • 1. Read the starter repo: github.com/krika2810/claude-code-sf-starter - every file commented.
  • 2. Copy it into your repo (one README command), edit CLAUDE.md for your org.
  • 3. Install the sf Code Analyzer plugin; run sf scanner run once locally.
  • 4. Add the CI templates, install the Claude Code GitHub Action, add ANTHROPIC_API_KEY to secrets.
  • 5. Open a PR and watch the gate run.
