Why this setup exists

The repo teaches Claude our standards. Hooks and CI enforce them.

The payoff

Claude's output lands inside our rules on the first pass - reviews get shorter, QA stops bouncing tickets back.

  • Without setup Claude guesses conventions from whatever Apex it happens to read first.
  • With setup standards, naming, and limits live in the repo - Claude reads them every session, and hooks block what rules forbid.
  • Quality is not negotiable. The bar for AI-written code is exactly the bar for human-written code.

Setup: memory files

CLAUDE.md - the file Claude reads every session

  • Project ./CLAUDE.md in git - the team's shared brain. Ours holds: sf commands, Apex/LWC standards, definition of done.
  • User ~/.claude/CLAUDE.md - personal preferences. Never shared with the team.
  • Keep it under ~200 lines. Long instruction files get followed less reliably. Push detail into rules and skills.
  • Modularize with @import - pull in standards files per package instead of one monolith.
  • Debug inconsistent behavior with the /memory command - it shows exactly which files loaded.

Source: Claude Code docs + Claude Certified Architect Foundations exam guide, Domain 3.1 (config hierarchy, scoping, modular organization).

Setup: path-scoped rules

Rules load only when relevant - that is the point

# .claude/rules/apex.md
---
paths: ["**/*.cls", "**/*.trigger"]
---
# Loaded only while Claude edits Apex. Costs zero tokens
# when the work is a Flow or a YAML file.
  • One file per topic: apex.md, lwc.md, flows.md, omnistudio.md, testing.md, git.md.
  • Glob patterns beat subdirectory CLAUDE.md files when conventions span directories (tests live everywhere).
  • Less irrelevant context = better answers and fewer tokens.

Source: Claude Certified Architect Foundations exam guide, Domain 3.3 (conditional convention loading).

Setup: skills

Skills: procedures Claude runs on demand

/apex-review

Reviews edited Apex against our rules: bulkification, CRUD/FLS, sharing, ApexDoc.

/deploy-validate

Deploy + test + scan a scratch org, in the right order, with proof at each step.

/scratch-org-setup

Creates and seeds a scratch org the same way, every time.

  • Skill vs CLAUDE.md: skills load when invoked; CLAUDE.md is always on. Universal standards go in CLAUDE.md, task procedures go in skills.
  • Frontmatter controls blast radius: context: fork runs the skill in an isolated sub-agent; allowed-tools restricts what it may call.

Source: Foundations exam guide, Domain 3.2 (commands and skills, context: fork, allowed-tools).

Setup: hooks

Hooks are the deterministic layer

The design rule

CLAUDE.md advises. Hooks enforce. Anything that must always happen gets a hook, not a sentence.

  • Deny list in settings.json - Claude cannot run sf org delete, hard-delete, or deploy to production aliases. Ever.
  • PostToolUse hook - every Apex file Claude edits is scanned for SOQL/DML in loops, hardcoded IDs, SeeAllData, empty catches.
  • Stop hook - Claude cannot end the session until tests pass and the scanner is clean (the definition of done).
  • Prompt instructions fail some percent of the time. For non-negotiables, that failure rate is not acceptable - use a hook.

Source: Foundations exam guide, Task Statements 1.4 and 1.5 (programmatic enforcement vs prompt-based guidance).

The mistake catalog

The six mistakes this setup is built to catch

  • Governor limits - code that works on 3 records and dies on 300.
  • SOQL and DML inside loops - the classic bulkification failure.
  • Wrong async choice - @future where a Queueable or Batch was needed.
  • Security gaps - missing CRUD/FLS checks, missing sharing, SOQL injection.
  • Coverage theater - tests that hit 75% and assert nothing.
  • Unscanned code - issues PMD and Code Analyzer flag in seconds, found by QA weeks later.

Each mistake maps to a rule file, a hook, or a CI gate. The next slides go through them.

Mistake 1: governor limits

Mistake 2: bulkification

SOQL and DML never go inside loops

Never 
for (Account a : Trigger.new) {
  Contact c = [SELECT Id FROM Contact
               WHERE AccountId = :a.Id];
  update a;
}
Always 
Map<Id, Contact> byAcct = new Map<Id, Contact>([
  SELECT Id, AccountId FROM Contact
  WHERE AccountId IN :Trigger.newMap.keySet()]);
List<Account> toUpdate = new List<Account>();
for (Account a : Trigger.new) { toUpdate.add(a); }
update toUpdate;
  • Query into collections before the loop. Act on collections inside it. DML once, after.
  • Triggers process up to 200 records at once - write every trigger as if it gets 200.
  • The PostToolUse hook flags SELECT or DML inside a loop the moment Claude writes it.
Mistake 3: async vs sync

Pick the async mechanism on purpose

Use it whenChains?Tracks?
@futureSimple fire-and-forget, primitives onlyNoNo
QueueableComplex types, needs job ID, needs chainingYesYes, via job ID
BatchLarge data volumes, up to 50M records via query locatorYes, in finish()Yes
SchedulableRuns on a clock, not on data eventsn/aYes
Default answer

Reaching for @future first is the smell. If you need chaining, complex parameters, or monitoring, it is Queueable. High volume means Batch.

Rules live in .claude/rules/apex.md so Claude proposes the right mechanism instead of the easiest one.

Mistake 4: security

Security is a first-class check, not a review afterthought

  • CRUD/FLS on every access. WITH USER_MODE in SOQL (default mode since API v67); Security.stripInaccessible() before DML on user-supplied data.
  • Sharing is declared, always. with sharing is the default; anything else needs a comment justifying it.
  • SOQL injection - no string-built queries with user input. Graph Engine (SFGE) traces data flow and finds the injection paths static rules miss.
  • No hardcoded IDs, profile names, or org URLs. PMD flags them; the hook flags them sooner.

Sources: Salesforce Apex security docs, Code Analyzer Graph Engine rules, PMD security ruleset (ApexCRUDViolation, ApexSharingViolations, ApexSOQLInjection).

Mistake 5: test quality

Coverage is a floor. Assertions are the point.

  • 75% coverage is the platform minimum to deploy. Our gate is 85% - set in CI, not in a wiki page.
  • PMD's test rules flag seeAllData=true and test methods with no assertions. Both are banned here.
  • Every test creates its own data, asserts behavior (not just execution), and covers the failure path too.
  • Claude generates tests to .claude/rules/testing.md - and the Stop hook will not let it finish until they pass.
Why this matters more with AI

Claude writes tests fast. Fast tests that assert nothing are worse than no tests - they fake confidence. The rules and the gate exist so speed never trades against proof.

Claude Code inside the pipeline

A fresh Claude reviews every PR - on purpose

  • Self-review is weak review. The session that wrote the code keeps its reasoning and defends its choices. An independent instance with no prior context catches what the author misses.
  • Headless mode for pipelines: claude -p "..." --output-format json - machine-parseable findings posted as PR comments.
  • The review prompt carries explicit criteria (our mistake catalog), not "be conservative" - vague instructions raise false positives and erode trust.
  • @claude in any PR comment summons help with full repo context (Claude Code Action, installed once).

Sources: Foundations exam guide Domains 3.6 and 4.6 (CI integration, independent review instances), anthropics/claude-code-action.

Using it well: orchestration

Big work gets a coordinator and sub-agents

  • Hub and spoke: one coordinator decomposes the task, spawns sub-agents, aggregates results. Sub-agents never talk to each other directly.
  • Sub-agent context is isolated. They inherit nothing automatically - the coordinator passes complete, structured findings in the prompt.
  • Spawn in parallel: independent investigations go out as multiple Task calls in one turn.
  • Scope the tools: 4-5 relevant tools per agent beats 18. Tool overload degrades selection reliability.

Source: Foundations exam guide, Domain 1 (27% of the exam): coordinator-subagent patterns, Task tool, parallel spawning, context passing.

Using it well: model choice

Match the model to the task - cost follows

ModelUse for
HaikuFast, cheap, simple: file scans, formatting, classification, boilerplate.
SonnetThe default. Day-to-day Apex/LWC development, tests, refactors.
OpusHard reasoning: architecture choices, nasty governor-limit debugging, security review.
  • Most tickets are Sonnet work. Spending Opus tokens on boilerplate is waste; asking Haiku to untangle a 200-record trigger bug is false economy.

Source: Claude Certified Architect Professional exam guide, Domain 2 (select models based on trade-offs) + Anthropic model docs.

Using it well: context rot

Long sessions decay. Manage context deliberately.

  • The symptom: Claude starts citing "typical patterns" instead of the classes it read an hour ago. Answers get vaguer as context fills.
  • Lost in the middle: models use the start and end of long inputs best. Put key facts at the top, not in the middle of a dump.
  • Keep exploration out of the main context: the Explore sub-agent reads widely and returns a summary; context: fork skills do the same.
  • Persist findings to scratchpad files in the repo; they survive compaction and crashes.
  • /compact early, and when prior results are stale, start fresh with a written summary - it beats resuming a rotten session.

Source: Foundations exam guide, Domain 5 (context management, scratchpads, summarization risks, session resumption).

Using it well: token efficiency

Fewer wasted tokens is a setup property, not willpower

  • Path-scoped rules load only for matching files - you stop paying for Apex rules while editing YAML.
  • Lean CLAUDE.md (~200 lines). It is prepended to every session; every line is a recurring cost.
  • Trim verbose tool output. A lookup that returns 40 fields when 5 matter taxes every later turn.
  • Prompt caching for repeated large contexts; Message Batches API for overnight work - 50% cheaper, 24-hour window, never for anything blocking a merge.
  • Right-size the model (previous slide) - the biggest single lever.

Sources: Foundations exam guide Domains 4.5 + 5.1, Professional guide Domain 2 (optimize context windows, token usage, caching).

Using it well: plan mode

Plan mode for thinking. Direct execution for typing.

PLAN MODE

Anything architectural: multi-file changes, library or API-version migrations, several valid approaches, touching a trigger framework. Explore and design first, implement after.

DIRECT EXECUTION

Well-scoped changes: a single-file bug fix with a clear stack trace, one validation check, a rename. No ceremony needed.

Rule of thumb

If the wrong approach would cost more than the planning would, plan first. Combine both: plan the migration, then execute the plan directly.

Source: Foundations exam guide, Domain 3.4 (plan mode vs direct execution, Explore subagent).

Using it well: prompting

Examples beat adjectives. Tests beat descriptions.

  • Show, don't describe. We pasted one short ApexDoc example into CLAUDE.md - Claude rewrote a poorly documented class in exactly our style. Two or three concrete input/output examples outperform any paragraph of rules.
  • Test-driven loop: write the tests first, then iterate by sharing failures. Each failure message is a precise instruction.
  • The interview pattern: on unfamiliar work, tell Claude to ask you questions before implementing. It surfaces decisions you did not know you were making.

Sources: Foundations exam guide Domains 3.5 and 4.2 (iterative refinement, few-shot prompting). The ApexDoc example ships in the starter repo's CLAUDE.md.

Responsible use

Rules for using Claude Code on this team

  • You review everything you merge. AI-written code you have not read is your code and your name on the commit.
  • Same bar as human code. Scanner clean, tests real, security checks present. "Claude wrote it" is never an excuse in review.
  • No secrets, ever. No credentials, session IDs, or customer data in prompts, CLAUDE.md, rules, or skills. MCP config uses environment variables, not pasted tokens.
  • Production is human-only. The deny list blocks Claude from destructive commands and prod deploys; do not weaken it without an architecture discussion.
  • Escalate doubt. If Claude's approach looks wrong for governor limits or sharing, it probably is - challenge it or ask a human.

Aligned with the Professional exam guide, Domain 5 (governance, safety, human-in-the-loop) and Anthropic's usage policies.

Get started

Ten minutes to a working setup

  • 1. Clone github.com/krika2810/claude-code-sf-starter and copy its files into your repo.
  • 2. Adapt CLAUDE.md: your commands, your package dirs. Delete the template comments.
  • 3. Copy the workflow files from ci-templates/ into .github/workflows/.
  • 4. Run sf code-analyzer run once for a baseline - fix or suppress what it finds, deliberately.
  • 5. Open your next PR. Watch the gate run and Claude's review land.
Then

Work one real ticket with Claude Code. Whatever breaks or annoys you - fix it in the rules, not in the chat. The setup gets smarter every sprint.
