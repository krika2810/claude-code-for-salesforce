Why we are doing this

Claude does not know our standards - until we write them down

  • Every session starts blank. Without setup files, you re-explain your standards every time - and you forget things.
  • Unguided Claude writes generic Salesforce code. SOQL inside loops, no CRUD/FLS checks, tests without real assertions.
  • Review becomes the bottleneck. Writing is the fast part; fixing what review catches is the slow part.
  • The fix: write the standards once, in the repo. Claude reads them every session, so the first draft already follows them.
The one rule underneath everything

AI-written code meets exactly the same bar as human-written code. The setup exists to make that cheap, not to lower the bar.

Part 1 - the basics (1 of 6)

Claude Code is a tool in your terminal that reads your repo and works with you

  • You type plain English, it does the work. It reads files, writes code, and runs commands - in the same terminal where you already run sf and git.
  • It drives the tools you already use. Ask it to deploy and it runs sf project deploy start. Ask about a pull request and it runs gh. No clicking through Setup, no hand-written API calls.
  • It is not autocomplete. You hand it whole tasks: "add a validation rule and deploy it to my scratch org" is one request, not fifty suggestions.
  • Everything it knows about our project comes from the repo. Which is exactly why the next five slides exist.
Part 1 - the basics (2 of 6)

Two words you will hear all day: context and tokens

Context

Everything Claude can see right now - the files it has read, your messages, its own replies. Think of it as a desk, not a warehouse: only so much fits. A Salesforce repo is far bigger than the desk, so what you put on it matters.

Tokens

The unit Claude reads and writes in - roughly three quarters of a word each. Every file it opens and every line it writes costs tokens, and tokens are what we pay for.

Why you should care

Good results and low cost are the same skill: give Claude the right context, not more context. Most of part 4 follows from this one idea.

Part 1 - the basics (3 of 6)

CLAUDE.md is a note Claude reads at the start of every session

  • It is a plain markdown file in the repo root. Claude reads it before you type a single word.
  • Put in what is always true: what the project is, the sf commands we use, our Apex and LWC standards, naming conventions, and what "done" means.
  • Salesforce example: our CLAUDE.md says service classes are named like AccountService and triggers delegate to handlers. Claude's first draft already follows those names.
  • Keep it short. It loads into every session, so every line costs tokens forever. If removing a line would not cause a mistake, cut it.
Part 1 - the basics (4 of 6)

Rules are detail that loads only when it is relevant

  • CLAUDE.md is always on; rules are not. Files in .claude/rules/ load only while Claude touches matching files.
  • Salesforce example: apex.md loads only while Claude edits a .cls or .trigger file. When you work on a Flow, the Apex rules stay out - zero tokens, no noise.
  • This is where the depth lives: bulkification, CRUD/FLS, sharing, governor limits, async choice, test standards - the things that used to be tribal knowledge.
  • One file per topic: apex.md, lwc.md, flows.md, testing.md, git.md.
Part 1 - the basics (5 of 6)

Skills are our procedures, written down once

  • A skill is a runbook Claude reads on demand - a written procedure it runs when the task matches, instead of you re-explaining the steps.
  • Salesforce example: /apex-review checks edited Apex against our rules - bulkification, CRUD/FLS, sharing. /deploy-validate runs deploy, tests, and scans in the right order, with proof at each step.
  • Skills sit between CLAUDE.md and rules: CLAUDE.md is what is always true, rules are what is true per file type, skills are how we do a task.
  • Write your first skill for whatever the team re-explains most often. Scratch org setup is a good candidate.
Part 1 - the basics (6 of 6)

Hooks turn advice into enforcement

  • CLAUDE.md advises; a hook cannot be talked out of it. A hook is a script that runs automatically on Claude's actions.
  • Salesforce example: our deny list means Claude can never run sf org delete or deploy to a production alias, no matter what anyone types.
  • Another: a hook scans every Apex file Claude edits for SOQL in loops and hardcoded IDs - while it works, not in review a week later.
  • Start without hooks. Add one the first time a standard gets ignored. Advice that never fails stays advice.
Part 1 - one more idea

Subagents are helpers with their own clean desk

  • A subagent is a second Claude with its own context. Send it the wide reading: "explore how AccountTriggerHandler works" comes back as a summary instead of twenty files filling your desk.
  • Your session stays clean for decisions; the reading happens somewhere else. Part 4 shows why this matters so much.
  • You will also hear about MCP - the way Claude connects to outside systems. Only connect what the task needs; every connected tool takes up desk space.
The six ideas, one line each

CLAUDE.md: always true. Rules: true per file type. Skills: how we do a task. Hooks: what cannot be skipped. Subagents: reading done elsewhere. Context and tokens: the desk everything sits on.

Part 3 - try it yourself

How the hands-on part works

  • I show a prompt, you type it - or your own version of it - against your scratch org. Declarative first, then code.
  • Watch what Claude does, not just what it answers. Which files does it open? Which commands does it run? What does it check before it calls something done?
  • When it drifts, correct it and watch it recover. That correction loop is the actual skill today.
  • Break things on purpose. Every prompt here runs safely in the starter repo and a scratch org.
The rhythm to learn

Type, watch, correct, repeat. Do not wait for the perfect prompt - there isn't one.

Part 3 - declarative (1 of 2)

Try it: a record-triggered Flow

# type this into Claude Code
Create a record-triggered Flow on Opportunity. When an
Opportunity is Closed Won, create a follow-up Task for the
owner, due in 7 days. Explain your choices as you go.
  • Watch: does it ask or check before writing? Good signs: it looks at the object's fields and existing automation first.
  • Watch: metadata, not mouse clicks. You want Flow metadata XML it can deploy - not a paragraph describing what to click in Setup.
  • Then say: "deploy it to my scratch org and show me it worked" - and watch it reach for sf on its own.
Part 3 - declarative (2 of 2)

Try it: a validation rule and a permission set

# type this into Claude Code
Add a validation rule on Opportunity: Amount must be over
1000 when Stage is Closed Won. Then create a permission set
called "Opportunity Manager" with edit access to
Opportunity. Deploy both.
  • Watch: two artifacts, one request. Notice it keeps both in its head and deploys them together.
  • Read the metadata before it deploys. You are still the reviewer - AI-written or not.
  • Then break it: rename a field to one that does not exist and re-deploy. Watching Claude work through a deploy error teaches you more than a clean run.
Part 3 - development (1 of 2)

Try it: an Apex class with real tests

# type this into Claude Code
Write an Apex service class AccountRatingService with a
method that recalculates ratings for a list of Accounts.
Follow our repo standards. Write the test class too, with
real assertions.
  • Watch: the rules load by themselves. Check the code is bulkified - no SOQL or DML inside loops - without you asking. That is part 1 paying off.
  • Watch: CRUD/FLS and sharing keywords should already be there. If they are not, that is a rules-file gap, not a Claude gap.
  • Then say: "run the tests" - it runs sf apex run test. Paste failures straight back; each failure message is a precise instruction.
Part 3 - development (2 of 2)

Try it: a Lightning web component

# type this into Claude Code
Build an LWC that shows an Account's open Opportunities in a
datatable, using an Apex controller with cacheable=true.
Follow our lwc.md rules.
  • Watch: the full bundle appears - .js, .html, .js-meta.xml, plus the controller class and its tests.
  • Watch: wire vs imperative. For a simple display it should reach for @wire with cacheable=true - the efficient default, not an imperative call on every render.
  • Then iterate in plain words: "deploy it", then "make the Amount column sortable". Small follow-ups are how real work feels.
Part 4 - working well (1 of 6)

Prompts that land the first time

  • Show, don't describe. We pasted one short ApexDoc example into CLAUDE.md and Claude matched our style exactly. Two or three concrete examples beat a page of adjectives.
  • Write the test first, then let Claude iterate on the failures. Each failure message is a precise instruction - much better than "make it better".
  • On unfamiliar work, have Claude interview you first. Answer its questions, let it write a spec, then start a fresh session to execute that spec.
  • Correct early. Stop it the moment it drifts (Esc). Two failed corrections in one session? Clear it and restart with a sharper prompt.
Part 4 - working well (2 of 6)

Plan first, then build

PLAN FIRST

Anything architectural: multi-file changes, data migrations, several valid approaches, touching a trigger framework. Explore and design first, implement after.

JUST DO IT

Well-scoped changes: a single-file bug fix with a clear stack trace, one validation check, a rename.

Rule of thumb

If the wrong approach costs more than the planning would, plan first. And start the plan from the outcome: "the trigger handles 200 records and the test proves it" tells Claude exactly when it is finished.

Part 4 - working well (3 of 6)

Keep your desk clean

  • The symptom of a full desk: Claude starts citing "typical patterns" instead of the classes it read an hour ago. Answers get vaguer as context fills up.
  • Send the wide reading to subagents - they explore and return summaries, so your session keeps only the decisions.
  • /clear between unrelated tasks. /compact early, before the desk is buried.
  • A fresh session with a written summary beats resuming a stale one. Ask Claude to write the handoff note, clear, and paste it in.
Part 4 - working well (4 of 6)

Split big work across a coordinator and subagents

  • One session coordinates; subagents do the pieces. The coordinator breaks the task down, spawns helpers, and assembles the results.
  • Split by question, not by file. Each subagent gets one question it can answer alone - "how does our trigger framework route events?", not "read these twelve classes".
  • Subagents start blank. The coordinator passes complete findings in the prompt - they inherit nothing automatically.
  • Our repo has an example: a security-reviewer agent that checks CRUD/FLS, sharing, and injection on demand.
Part 4 - working well (5 of 6)

Pick the right model - cost follows

ModelUse it for
HaikuFast and cheap: file scans, formatting, boilerplate.
SonnetThe default. Day-to-day Apex, LWC, tests, refactors.
OpusHard reasoning: architecture choices, nasty governor-limit debugging, security review.
The default

Sonnet for the day job. Drop to Haiku for grunt work, go up to Opus when the task earns it. Model choice is a per-task decision, not a setting you pick once.

Part 4 - working well (6 of 6)

Saving tokens is a setup property, not willpower

  • Path-scoped rules load only for matching files - you stop paying for Apex rules while editing YAML.
  • A lean CLAUDE.md. It loads into every session; every line is rent you pay forever.
  • Right-size the model. The biggest single lever, and it is one word in your prompt.
  • Overnight work goes through the batch API - half the price, and fine for anything not blocking a merge.

Notice what is not on this list: "type shorter prompts". Token savings come from how the setup is built, not from developers censoring themselves.

Part 4 - the ground rules

The rules we all follow when Claude writes our code

  • You review everything you merge. AI-written code you have not read is still your code, and your name is on the commit.
  • Same bar as human code. Scanners clean, tests real, security checks present.
  • No secrets, ever. No credentials, session IDs, or customer data in prompts, CLAUDE.md, rules, or skills.
  • Production stays human-run. A person deploys to prod, not Claude.
  • Escalate doubt. If Claude's approach looks wrong, challenge it or ask a human.
