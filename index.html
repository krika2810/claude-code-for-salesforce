The problem

Why we are doing this

The point: our mistakes are predictable, so they are preventable. The fix is to write the standards down where the tools can enforce them.
  • The same classes of mistake keep reaching QA: governor-limit violations, SOQL in loops, missing CRUD/FLS checks, weak tests.
  • When the pipeline fails, we run it again. Every rerun is developer time spent waiting instead of building.
  • Code review spends time on naming, formatting, and known anti-patterns. That is machine work. Review should be about design.
  • We now have Claude Code writing code with us. An AI assistant writes fast in every direction, including the wrong one, unless the repo tells it what "right" means here.
The mistake catalog

Six mistakes that cost us the most

The point: these are the patterns the setup in this deck is built to catch before QA does.

1. Governor limits

Code that works for one record and fails in production at volume.

2. No bulkification

SOQL queries and DML statements inside loops.

3. Wrong async choice

Future methods used where Queueable or Batch was the right tool.

4. Security gaps

Missing sharing keywords, no CRUD/FLS enforcement, SOQL injection.

5. Weak tests

SeeAllData=true, no asserts, single-record tests only.

6. Hygiene

Hardcoded IDs, debug statements, empty catch blocks, missing ApexDoc.

Mistake 1 · Governor limits

Know the numbers you are coding against

The point: Apex runs in a multitenant environment, so the platform enforces per-transaction limits. Code that exceeds one fails with an exception you cannot catch.
Per-transaction limitSynchronousAsynchronous
SOQL queries issued100200
Records retrieved by SOQL50,00050,000
DML statements150150
Records processed by DML10,00010,000
CPU time10,000 ms60,000 ms
Heap size10 MB25 MB
Callouts per transaction100100

Source: Salesforce Apex Developer Guide, "Execution Governors and Limits". Batch Apex resets these for each execute() batch. Scheduled Apex runs under synchronous limits.

Mistake 2 · Bulkification

SOQL and DML never go inside loops

The point: triggers can receive 200 records at once. A query inside a loop that passes a single-record test can fire 200 times in production and hit the 100-query limit.

Fails at volume

for (Account a : Trigger.new) {
  // one query per record
  Contact c = [SELECT Id FROM Contact
    WHERE AccountId = :a.Id LIMIT 1];
  update c; // one DML per record
}

Bulkified

Map<Id, Account> byId =
  new Map<Id, Account>(
    [SELECT Id, (SELECT Id FROM Contacts)
     FROM Account WHERE Id IN :Trigger.new]);
List<Contact> toUpdate = new List<Contact>();
for (Account a : Trigger.new) {
  toUpdate.addAll(byId.get(a.Id).Contacts);
}
update toUpdate; // one DML total

PMD catches this automatically: the rules OperationWithLimitsInLoop and AvoidNonRestrictiveQueries are in our ruleset.

Mistake 3 · Async decisions

Pick the async mechanism on purpose

The point: "make it @future" is not an answer. Each async option exists for a specific shape of work.
MechanismUse it whenDo not use it when
@futureSimple fire-and-forget work, for example a callout. Only primitive parameters.You need sObjects, chaining, or monitoring.
QueueableYou need complex parameter types, job chaining, or a job ID to monitor.You are processing thousands of records.
Batch ApexLarge data volumes; records processed in chunks with fresh limits per batch.The job is small and latency matters.
SchedulableThe work is time-based: nightly rollups, periodic syncs.The trigger is a data event, not a clock.

Also enforced: no callouts after DML in the same transaction, and at most 50 queueable jobs enqueued per transaction (1 from inside async context).

Mistake 4 · Security

Security gaps the scanners already know how to find

The point: these were not in the original checklist, and they are the ones a security review will find first.

Sharing and CRUD/FLS

  • Every class declares sharing. with sharing is the default; anything else needs a comment saying why.
  • Use WITH USER_MODE on SOQL over user-driven queries.
  • Use Security.stripInaccessible() before DML on request data.

Injection and leaks

  • String-built SOQL needs String.escapeSingleQuotes. Prefer bind variables.
  • No hardcoded record IDs, profile names, or org URLs.
  • No System.debug without a logging level in committed code.

PMD security rules: ApexSharingViolations, ApexCRUDViolation, ApexSOQLInjection, AvoidHardcodingId. The Graph Engine goes further: it follows data flow through the whole call path, so it catches violations that single-file analysis misses.

Mistake 5 · Tests

Coverage is a floor, not a goal

The point: 75% coverage is the platform minimum to deploy. It says nothing about whether the tests prove anything.

Rejected in review

  • @isTest(SeeAllData=true) - tests must create their own data.
  • Test methods with no assert. PMD rule ApexUnitTestClassShouldHaveAsserts.
  • Single-record trigger tests only. Test with 200 records.

Expected

  • Test.startTest() / stopTest() around the code under test.
  • Asserts on behavior, not just "no exception".
  • Tests named method_condition_expectedResult.
  • Team gate: 85% org-wide coverage in CI, not 75%.
Coverage

The setup covers all four build surfaces

The point: standards exist per surface, because the mistakes are different on each one.

Apex

Bulkification, sharing and CRUD/FLS, one trigger per object with logic in handlers, deliberate async choices, ApexDoc on public classes and methods.

LWC

Wire adapters before imperative calls, cacheable=true for reads, handled promise rejections, ESLint clean, Jest tests for new components.

Flow

Before-save for same-record updates, after-save for related work, no data elements inside loops, every fault path connected. Code Analyzer v5 includes a Flow Scanner engine.

OmniStudio

Naming prefixes (DR_, IP_, OS_, FC_), Integration Procedures for server-side logic, new versions instead of editing active components.

The assistant

What Claude Code adds on top

The point: scanners catch mistakes after they are written. Claude Code reads the same standards from the repo and applies them while writing.

CLAUDE.md + rules

Instructions in the repo that Claude reads every session. This is where the standards live.

Skills

Named procedures (for example /apex-review) Claude runs on demand, so checklists do not depend on memory.

Hooks

Shell commands that fire automatically on events. The deterministic layer: they run even if Claude forgets.

Then CI repeats the same checks on every pull request, so nothing depends on one person's local setup.

Setup · Layer 1

CLAUDE.md: the standards file

The point: CLAUDE.md is read at the start of every session. Put what you would otherwise re-explain: commands, conventions, definition of done. Keep it under about 200 lines - longer files get followed less reliably.
ScopeLocationUse for
Project (shared via git)./CLAUDE.mdTeam standards, commands, architecture.
User (personal)~/.claude/CLAUDE.mdYour own preferences across projects.
Local (gitignored)./CLAUDE.local.mdPersonal scratch settings for this repo.

Write instructions that can be checked: "Run sf apex run test -o dev before committing", not "test your changes". Subdirectory CLAUDE.md files load when Claude works in those directories. Files can import others with @path/to/file.

Setup · Layer 2

.claude/rules: detail that loads only when relevant

The point: a rule scoped to **/*.cls loads only when Claude touches Apex. Detail costs nothing when it is not needed.
.claude/rules/
├── apex.md        # paths: **/*.cls, **/*.trigger
├── lwc.md         # paths: force-app/**/lwc/**
├── flows.md       # paths: force-app/**/flows/**
├── omnistudio.md  # paths: force-app/**/omni*/**
├── testing.md     # paths: **/*Test.cls, **/__tests__/**
└── git.md         # always loaded

The governor-limits table, the async decision criteria, the ApexDoc style example, and the security checklist live in these files, not in the root CLAUDE.md.

Setup · Layer 3

Skills: procedures on demand

The point: a skill is a SKILL.md file with instructions Claude follows when the skill runs. The body loads only when invoked, so long checklists are free until needed.
.claude/skills/
├── apex-review/SKILL.md       # 10-point Apex review checklist
├── deploy-validate/SKILL.md   # dry-run deploy + tests before QA
└── scratch-org-setup/SKILL.md # create, push, permsets, smoke test

Invoke directly with /apex-review, or Claude loads the skill itself when the description matches the task. The description field in the frontmatter is what Claude uses to decide.

Setup · Layer 4

Hooks: the deterministic layer

The point: CLAUDE.md and rules advise; hooks enforce. They are shell commands that fire on events, whether or not Claude remembers the standard.

Guardrails (settings.json)

  • Denied commands Claude cannot run: sf org delete, sf data delete, deploys to prod aliases.
  • Allowed list for the everyday sf commands, so sessions do not stall on permission prompts.

Event hooks

  • PostToolUse on Edit/Write of a .cls file: run Code Analyzer on that file immediately.
  • Stop hook: restate the definition of done (tests run, scanner run, verification stated) when Claude finishes.

A PreToolUse hook can block a tool call outright. That is the mechanism for rules that must never be broken, regardless of context.

Working smart

Pick the model for the task

The point: model choice is the biggest cost and quality lever. Match the model to the job instead of leaving the most expensive one on by default.
ModelUse it for
sonnetDaily coding work: features, fixes, tests. The right default.
opusComplex architectural decisions and multi-step reasoning. Switch deliberately.
haikuFast, simple tasks. Ideal for subagents doing mechanical work.
opusplanOpus during plan mode, then Sonnet executes the plan.

Switch mid-session with /model, or set the default in /config. High unexpected spend usually traces back to Opus left on as the default.

Working smart

Context rot and token efficiency

The point: every token in the context window costs money on every message and dilutes attention. Keep context small and fresh.
  • Clear between unrelated tasks with /clear. Stale context is paid for again on every message. /rename first, /resume to return later.
  • Compact with instructions: /compact Focus on the failing tests keeps what matters when the session grows long.
  • Keep CLAUDE.md under 200 lines. Move procedures into skills, which load only when invoked, and detail into path-scoped rules, which load only for matching files.
  • Delegate verbose work to subagents - test runs, log analysis, doc fetching. The bulk stays in the subagent's context; only the summary returns to yours.
  • Check /context to see what is consuming space, and prefer CLI tools like sf and gh over MCP servers where both exist.
  • Enterprise average: about $13 per developer per active day. Untracked usage is how teams blow past that.
Working smart

Agent orchestration

The point: one long session doing everything is the expensive, error-prone pattern. Split work across focused agents with their own context.

Subagents

  • Each subagent gets its own context window; only its summary returns.
  • Set model: haiku on subagents doing simple, mechanical tasks.
  • Good fits: running the test suite, scanning logs, researching a docs question.

Skills as the division of labor

  • Each of our skills is one well-scoped job: review, validate, set up.
  • Skills can run inside a subagent, keeping even the review output out of your main context.
  • Token use scales with active agents - spawn what the task needs, no more.
Working smart

Responsible use rules for developers

The point: Claude is fast in every direction, including the wrong one. These rules keep speed from becoming risk.
  • You own the merge. Review every change Claude writes. The PR gates help; they do not replace reading the diff.
  • Enforce with hooks, not hope. CLAUDE.md is context Claude usually follows. Hooks and deny lists are guarantees. Anything that must never happen goes in a hook.
  • Never commit secrets. Auth URLs, tokens, and org credentials stay out of the repo. CI uses GitHub secrets; locally use sf auth, not files.
  • Least privilege in CI. The Claude GitHub App and the Dev Hub secret get exactly the permissions the workflows need.
  • Watch usage. Run /usage. If spend jumps, look for long stale sessions and default-model drift before anything else.
  • Data stays in scope. Do not paste production customer data into prompts. Use sandbox data.
Proof from our own work

One example taught the style

The point: a short example in context beats a page of rules.

Last week we were fixing PMD errors, and one of them was ApexDoc written in poor English. We gave Claude one short example of the style we wanted, and it picked the style up and rewrote the rest correctly.

That is why the setup files ship with concrete examples: the ApexDoc block in .claude/rules/apex.md, the naming table in docs/naming-conventions.md, the bulkified query in this deck. Claude imitates examples far more reliably than it obeys abstract instructions. When you correct Claude once, add the correction to the rules file so you never make it twice.

Research additions

What the research added to the original list

The point: the starting list was governor limits, PMD, Code Analyzer, Graph Analyzer, async versus sync, and bulkification. Researching the official docs surfaced these gaps.
  • Security rules as first-class checks: sharing keywords, CRUD/FLS enforcement, and SOQL injection have dedicated PMD rules and Graph Engine data-flow rules.
  • Test quality rules, not just coverage: PMD flags SeeAllData=true and tests without asserts.
  • Flow Scanner: new in Code Analyzer v5 - Flows get scanned like code now.
  • RetireJS and CPD: vulnerable JavaScript dependencies and duplicated code blocks, both bundled in Code Analyzer.
  • OmniStudio naming conventions as a written standard (DR_, IP_, OS_, FC_ prefixes).
  • Hooks as the deterministic layer, so enforcement does not depend on the model remembering.
  • Path-scoped rules (.claude/rules/), so Apex detail loads only for Apex work.
  • Model selection, context hygiene, orchestration, and responsible-use rules drawn from the Claude Code docs and Anthropic's certification material.
  • Hardcoded IDs, debug statements, empty catch blocks, logic in triggers - all covered by named PMD rules in the ruleset.
The payoff

What this buys us

The point: developer time goes to building, the QA pipeline passes the first time, and quality goes up instead of being traded away.

Time back

No pipeline reruns for known anti-patterns. No review rounds about names and formatting. No rediscovering setup steps.

First-pass QA

Deployments are validated with tests before the real run. Coverage gate is enforced in CI, not discovered in QA.

Quality up

Standards are enforced by hooks and CI on every change, human-written or AI-written, so speed does not erode them.

Rollout

Get started this week

The point: everything in this deck is already built as a starter template. Clone it, tweak the marked spots, and it is yours.
  • Clone the starter repo: github.com/krika2810/claude-code-sf-starter
  • Edit CLAUDE.md first - project overview, org aliases, standards. This file is read every session.
  • Adapt docs/naming-conventions.md to your org, then keep it stable.
  • Add the two repo secrets: SFDX_AUTH_URL and ANTHROPIC_API_KEY; install the Claude GitHub App.
  • Verify locally: run /context in Claude Code to confirm the files load, then run /apex-review on a real file.
  • Open a PR and watch CI plus the Claude review run.
