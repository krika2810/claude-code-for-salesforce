Claude Code

Plan, build, test, review, and ship from one development session.

Why developers use it

Claude Code works across the development lifecycle

Without Claude Code

Search the repo. Read docs. Edit files. Switch to the terminal. Run tests. Read errors. Repeat.

With Claude Code

Describe the outcome once. Claude reads, edits, runs tools, checks the result, and shows the diff.

Explore  →  Plan  →  Build  →  Test  →  Review  →  Ship
   reads       asks       edits       runs        shows       opens
   code        first      files       checks      diff        PR
  • Less tool switching. The work stays in one terminal session.
  • Faster feedback. Claude reads test failures and fixes the next issue.
  • Developer stays in control. You approve the plan, diff, and merge.
Part 1 - the ideas (1 of 8)

Claude Code is a development agent

> Find why login fails after a password reset. Fix it and run the tests.

● Searches the repository for the reset and login flow
● Reads the relevant code and recent test failures
● Edits two files and adds a regression test
● Runs the test command and reports the diff
  • Agent means action. It can read files, edit code, and run commands.
  • It uses your tools. Git, the shell, tests, linters, and connected services.
  • You set the boundary. Permissions decide what it may read or change.
Part 1 - the ideas (2 of 8)

Context is Claude's working memory

What enters context

Your prompts, files Claude reads, command output, tool results, and Claude's replies.

Why tokens matter

Tokens measure that text. As the window fills, old and unrelated details compete for attention.

/context
System tools           18k
CLAUDE.md + rules       6k
Files and commands     82k
Conversation           34k
Use /compact to keep the useful parts. Use /clear for a new task.
  • Load only what the task needs. Do not ask Claude to read the whole repo.
  • Start fresh between unrelated tasks. Old work can pull the next answer off course.
Part 1 - the ideas (3 of 8)

CLAUDE.md holds shared project instructions

# CLAUDE.md - commit this file
## Build and test
- npm run build
- npm test -- --runInBand

## Architecture
- API handlers call service modules.
- Database access stays in repositories.

## Definition of done
- Tests pass. Lint is clean.
- Update docs for public APIs.
Put this in

Commands, architecture boundaries, naming rules, common mistakes, and the checks required before completion.

Keep this out

Task-specific requests, long tutorials, copied docs, secrets, and rules that apply to only one file type.

  • Claude reads it at session start. Every line uses context, so keep it short.
  • Use /init for a draft. Then review every line with the team.
  • Use imports or rules for detail. CLAUDE.md should point, not become a handbook.
Part 1 - the ideas (4 of 8)

Rules add instructions for matching files

# .claude/rules/api-tests.md
---
paths: ["src/api/**/*.ts", "tests/api/**/*.ts"]
---
- Validate every request at the boundary.
- Cover success, invalid input, and permission failure.
- Mock external calls. Do not mock the service under test.
  • Path-scoped. This rule loads only while Claude works on matching files.
  • More specific than CLAUDE.md. Put framework and file-type detail here.
  • Lower context cost. Front-end rules do not load during database work.
Part 1 - the ideas (5 of 8)

Skills store a repeatable procedure

# .claude/skills/pr-review/SKILL.md
---
name: pr-review
description: Review the current diff
---
1. Read the diff and changed tests.
2. Check behavior, security, and errors.
3. Run the smallest relevant test set.
4. Report findings by severity.
> /pr-review

High  auth.ts:88
Missing permission check

Medium  user.test.ts
No invalid-token test

Passed  24 focused tests
  • Use a skill when steps repeat. Review, release, migration, or incident checks.
  • Loads when needed. The full procedure does not sit in every session.
Part 1 - the ideas (6 of 8)

Hooks run checks at fixed points

# .claude/settings.json
"hooks": {
  "PreToolUse": [{
    "matcher": "Bash",
    "hooks": [{
      "type": "command",
      "command": ".claude/hooks/check-command.sh"
    }]
  }]
}
● Bash: rm -rf ./data
✕ Blocked by hook
Destructive commands need approval.

The command did not run.
  • PreToolUse checks an action before it runs.
  • PostToolUse checks the result after a tool finishes.
  • Stop can require tests or another completion check before Claude stops.

Part 4 - working well (4 of 5)

Reduce token use

  • Use path-scoped rules. Apex rules do not load while you edit a Flow.
  • Keep CLAUDE.md short. Every line loads into every session.
  • Choose the right model. Use smaller models for simple work.

Part 4 - the ground rules

Review and protect every change

  • Review every change before you merge it.
  • Use the same checks as human-written code. Run tests and fix analyzer findings.
  • Do not add secrets. Keep credentials and customer data out of prompts and setup files.
  • Keep production deployment manual. A developer approves and runs it.

Review later - Boris Cherny thread (1 of 3)

Run independent tasks in parallel worktrees

# one branch and directory per session
git worktree add ../app-auth feature/auth
git worktree add ../app-api feature/api
git worktree add ../app-analysis analysis

(cd ../app-auth && claude)
(cd ../app-api && claude)
(cd ../app-analysis && claude)
  • Team pattern: run three to five sessions when the tasks do not depend on one another.
  • Name worktrees clearly. Short shell aliases make switching quick.
  • Keep an analysis worktree. Use it for logs, queries, and investigation without touching feature branches.
  • Do not share a working directory. Two sessions editing the same files will overwrite or confuse each other.

Review later - Boris Cherny thread (2 of 3)

Use plan mode before complex work

# first session writes the plan
> Read the current implementation,
  tests, and constraints. Ask questions.
  Write the plan. Do not edit files.
# second session reviews it
> Review this plan as a staff engineer.
  Find missing migrations, failure modes,
  tests, and rollout risks.
  • Spend effort before implementation. A better plan reduces corrections later.
  • Re-plan when the work goes wrong. Do not keep pushing a weak approach.
  • Plan verification too. Decide which tests, logs, screenshots, or benchmarks prove the result.
  • Separate author and reviewer. A fresh session can challenge assumptions without inheriting the first session's reasoning.

Review later - Boris Cherny thread (3 of 3)

Turn corrections into project memory

> Update CLAUDE.md so you do not make that mistake again.

Before adding a rule, check:
1. Did this mistake actually happen?
2. Does the rule apply to the whole project?
3. Can the instruction be one clear sentence?
4. Can a test or hook enforce it instead?
  • Use real failures as input. Do not fill CLAUDE.md with generic advice.
  • Edit it ruthlessly. Remove rules Claude follows without being told and rules that no longer apply.
  • Track longer project notes separately. Keep task or PR notes in a directory and link to them.
  • Measure the result. The file is useful only if repeated mistakes fall.

Review later - 50 Claude Code Tips (2 of 5)

Give Claude a verification loop

> Implement the change. Then run:
  npm run build
  npm test -- --runInBand
  npm run lint
Read every failure, fix it, and repeat. Stop only when all three pass.
  • Name the exact commands. “Make sure it works” is not a test.
  • Let Claude read the failure. Build output, test output, logs, browser state, or performance traces become the next input.
  • Use the smallest useful check first. Focused tests give faster feedback; run the full suite before completion.
  • Match the check to the product. Web work can use browser automation; mobile work can use device logs; performance work can use traces.

Source: John Kim, “50 Claude Code Tips To Get You Started”: getpushtoprod.substack.com/p/50-claude-code-tips-to-get-you-started

Build the plan before Claude builds the code

What

State the outcome, files or area, expected behavior, and what must not change.

Domain

Point Claude to architecture notes, examples, constraints, and existing patterns.

Validation

Name the commands or observations that prove the task is complete.

Challenge the plan

Ask about failure modes, migration, rollback, permissions, and tests before editing.

  • Plan mode is for shared understanding. Use it to find wrong assumptions early.
  • Do not over-plan a one-line change. Match planning effort to risk and scope.

Use permissions and hooks deliberately

# allow routine tools
/permissions
  Read
  Edit
  Bash(npm test:*)
  Bash(npm run lint:*)
# enforce a hard rule
PreToolUse
  block destructive commands

PostToolUse
  format edited files
  run focused checks
  • Use allowlists for routine commands. Keep approval for risky or broad actions.
  • Use skip-permissions only in a throwaway environment. It is not a normal project setting.
  • Hooks are deterministic. Put must-run checks there instead of hoping an instruction is followed.

Review later - CLAUDE.md guide (2 of 3)

Write instructions that change behavior

# weak
- Write clean code.
- Follow best practices.
- Be careful with errors.
# useful
- Use named exports only.
- Return Result types; do not throw
  from service modules.
- Keep tests beside source as
  *.test.ts.
  • Describe observable behavior. Claude must be able to tell whether it followed the rule.
  • Include commands and locations. State where code lives and how to build or test it.
  • Record non-obvious choices. Import paths, error patterns, environment sources, and naming that Claude might guess wrong.
  • Remove generic expertise claims. They add tokens without guiding a decision.

Review later - CLAUDE.md guide (3 of 3)

Keep guidance short; enforce guarantees elsewhere

Delete the line when

Claude already does it reliably, it repeats documentation, it is obsolete, or it applies to one temporary task.

Move the line when

It is file-specific: use a rule. It is a procedure: use a skill. It must always happen: use a hook or test.

Monthly CLAUDE.md review
1. Which mistakes repeated?
2. Which rules were ignored?
3. Which rules are vague or duplicated?
4. Which checks can become tests or hooks?
5. Does every remaining line still earn its context cost?

Use Claude Code to build a checked CI workflow

> Add a GitHub Actions workflow that rebuilds the README index.
  Inspect the repository first. Use current action versions.
  Run the generator locally. Show the generated diff.
  Validate the workflow file before finishing.
  • Start with a small real feature. The article used an automatically updated README index.
  • Let Claude inspect the repository. Existing scripts and file layout should drive the workflow.
  • Check generated configuration. Action versions, permissions, triggers, and paths can become stale or unsafe.
  • Keep the transcript. A recorded session makes the process reviewable and repeatable.

Give code research a clear deliverable

> Research how this library handles retries.
  Read source, tests, issues, and release notes.
  Run a small experiment for each retry mode.
  Save findings in research/retries.md with links,
  commands, outputs, and open questions.
  • Ask a research question, not “explore this repo.”
  • Provide a useful environment. Source, dependencies, test tools, and network access decide what can be proven.
  • Require an artifact. A report or pull request survives after the session ends.
  • Ask for experiments. Running code gives stronger evidence than reading alone.

Review later - Simon Willison (3 of 3)

Use a separate repository for open-ended research

Why separate it

The agent can create files, install tools, and run experiments without risking the product repository.

Public or private

Use a public research repo for shareable work. Use a private one when the question or data is not ready to publish.

Review the pull request

Check sources, commands, generated files, experiment design, and whether the conclusion follows from the evidence.

Keep boundaries

Do not put credentials, customer data, or unrelated production access into the research environment.

Review later - senior engineer Reddit thread (2 of 2)

Parallel sessions need isolation and integration

# split by independent outcome
feature/auth      → session A → focused tests → PR A
feature/api       → session B → focused tests → PR B
bugfix/login      → session C → regression test → PR C

# developer integrates
review each diff → resolve shared assumptions → run full suite → merge
  • Use one worktree per session. Separate directories prevent file collisions.
  • Split by outcome, not by arbitrary file count. Each branch needs a clear acceptance test.
  • Pre-orient the agent. A maintained project map or concise CLAUDE.md reduces repeated discovery.
  • Budget for integration. Parallel branches can still make conflicting architecture choices.

Review later - combined operating model

A complete Claude Code working loop

01
Orient

Read CLAUDE.md, project map, and relevant rules.

02
Plan

Ask questions. List files, risks, and checks.

03
Implement

Make the smallest coherent change.

04
Verify

Build, test, lint, inspect UI or logs.

05
Review

Read the diff and challenge assumptions.

06
Learn

Save a real repeated lesson in rules or tests.

  • Use subagents for bounded reading. Keep core implementation where the full context lives.
  • Use worktrees for independent outcomes. Integrate through reviewed pull requests.
  • Automate guarantees. Tests and hooks are stronger than prose instructions.
